# ارزیابی معماری لانچر ویندوز و تناسب Supabase

تاریخ بررسی: ۲۰۲۶-۱۱-۰۱ — بررسی مستندات رسمی و کد موجود مخزن.

> به‌روزرسانی دامنه با تصمیم کاربر: فایل‌ها روی آپلودرهای رایگان و مستقل می‌مانند؛ انتخاب/تغییر میزبان دانلود و R2 جزو کار فعلی نیست. پیشنهادهای میزبانی این سند صرفاً مقایسه اولیه‌اند، نه تصمیم اجرایی. طرح امنیتی جدید و مبنای آماده‌سازی ساخت در `docs/security-design-fa.md` است. فعلاً فقط بررسی و طراحی مستند مجاز است؛ پیاده‌سازی منتظر دستور صریح کاربر می‌ماند.

این سند پیشنهاد معماری است، نه پیاده‌سازی یا گواهی امنیت/کارایی. هیچ پروژه، جدول، کلید یا سرویس ابری ایجاد یا تغییر داده نشده است. بررسی کد ایستا بوده؛ برنامه روی ویندوز اجرا و آزمون بار انجام نشده است. اعداد تعرفه باید پیش از خرید و انتشار دوباره کنترل شوند.

## ۱. تصمیم پیشنهادی

**Supabase برای Backend مدیریتی و لایسنس این پروژه مناسب است؛ برای جایگزین‌کردن تمام زیرساخت‌ها با یک سرویس، خیر.**

پیشنهاد پایه:

- Tauri 2 + Rust برای لانچر و عملیات محلی حساس، در صورت تأیید مهاجرت از Electron موجود.
- Supabase Postgres برای داده‌های مرکزی.
- Supabase Edge Functions برای API لایسنس، مجوز دانلود و عملیات حساس مدیران.
- Supabase Auth برای مدیران، همراه TOTP MFA و نقش‌های اختصاصی پروژه.
- Cloudflare Pages برای فایل‌های استاتیک پنل مدیریت.
- میزبان دانلود مستقل یا R2 خصوصی برای فایل‌های بازی؛ دانلود مستقیم به دستگاه کاربر.
- بدون VPS در معماری اولیه؛ بدون نیاز به D1 در کنار Postgres برای نگهداری همان داده‌ها.

Workers را فقط در صورت نیاز مشخص به درگاه مشترک، کنترل سوءاستفاده در لبه یا دسترسی کنترل‌شده به R2 اضافه کنید. استفاده هم‌زمان از دو Backend برای منطق یکسان، پیچیدگی و خطای امنیتی ایجاد می‌کند.

## ۲. وضعیت واقعی مخزن

بر مبنای `package.json`، `main.js`، `preload.js` و فایل‌های `src`:

| بخش | وضعیت مشاهده‌شده |
|---|---|
| چارچوب دسکتاپ | Electron؛ در مخزن فعلی Tauri/Rust وجود ندارد |
| رابط | HTML/CSS/JavaScript، زبان فارسی/انگلیسی و حالت شب/روز |
| مسیر بازی | انتخاب دستی، تشخیص ساده مسیرهای رایج Steam و بررسی وجود `acs.exe` و `content` |
| تنظیمات و Manifest | JSON محلی در userData |
| عملیات فایل | IPC کپی با بکاپ ساده و بازگردانی/حذف |
| موتور دانلود و نصب | پیاده‌سازی کامل مشاهده نشد |
| لایسنس و API مرکزی | مشاهده نشد |
| پنل مدیریت و Migration دیتابیس | مشاهده نشد |
| ZIP/RAR/7z | وابستگی‌های ZIP و RAR در package.json؛ موتور نصب کامل و پشتیبانی اجرایی 7z مشاهده نشد |
| تست خودکار | اسکریپت یا مجموعه تست مشاهده نشد |

README نسبت به کد عقب است: صفحات gamePath و baseModsCheck اکنون وجود دارند، ولی هنوز در فهرست بخش‌های ساخته‌نشده README آمده‌اند. پس نه می‌توان پروژه را آماده انتشار دانست و نه همه چیز را صرفاً یک طرح بدون کد حساب کرد.

### ریسک‌های قابل مشاهده در کد فعلی

- `fs:copy-with-backup` و `fs:restore-or-delete` مسیرهای ورودی را بدون محدودسازی به ریشه بازی/محل بکاپ دریافت می‌کنند. این سطح دسترسی باید در لایه Native محدود شود؛ اعتبارسنجی UI کافی نیست.
- `shell:open-external` طرح URL و مقصد را محدود نمی‌کند؛ برای لینک‌های بیرونی allowlist و HTTPS لازم است.
- در `src/index.html` سیاست CSP مشاهده نشد. `contextIsolation: true` و `nodeIntegration: false` نقاط مثبت‌اند، اما جای کنترل ورودی IPC را نمی‌گیرند.
- مسیر ذخیره‌شده در صفحه gamePath داخل `innerHTML` قرار می‌گیرد؛ برای متن مسیر باید `textContent` استفاده شود.
- بکاپ‌ها با نام پوشه والد و نام فایل ساخته می‌شوند؛ در مسیرهای متفاوت امکان برخورد نام و بازنویسی بکاپ وجود دارد. شناسه تراکنش + مسیر نسبی کامل نیاز است.
- JSONهای تنظیمات و Manifest امضا نشده‌اند و با نوشتن مستقیم ذخیره می‌شوند. برای اشتراک مرجع اعتماد نیستند؛ برای پایداری نصب نیز نوشتن اتمیک، اعتبارسنجی و بازیابی خرابی لازم است.
- عملیات همگام فایل می‌تواند Main Process را هنگام کپی فایل‌های حجیم مسدود کند.
- اعتبارسنجی فعلی وجود فایل/پوشه را می‌سنجد؛ نوع واقعی فایل، اجازه نوشتن، فضای آزاد و مسیر canonical را تضمین نمی‌کند.

این‌ها یافته‌های ایستا هستند، نه ادعای اثبات بهره‌برداری. مهاجرت به Rust به‌تنهایی این خطاهای طراحی را برطرف نمی‌کند.

## ۳. Supabase دقیقاً چه قسمت‌هایی را پوشش می‌دهد؟

| نیاز | ارزیابی |
|---|---|
| کاربران منطقی/دستگاه‌ها، اشتراک و لایسنس | مناسب؛ مدل سفارشی در Postgres |
| کاتالوگ، نسخه‌ها، وابستگی‌ها و مراحل نصب | مناسب؛ داده رابطه‌ای + JSONB اعتبارسنجی‌شده برای تنظیمات |
| جلوگیری از فعال‌سازی هم‌زمان روی دو دستگاه | مناسب با تراکنش/قفل یا به‌روزرسانی شرطی و قیود یکتا |
| ورود چندمدیره | Auth مناسب؛ نقش‌های کسب‌وکار باید پیاده‌سازی شوند |
| MFA مدیران | TOTP موجود و رایگان است [۴] |
| API و امضای مجوز | Edge Functions مناسب برای درخواست کوتاه؛ منطق لایسنس آماده نیست |
| مجوز آفلاین ۳+۷ روز | قابل ساخت؛ قابلیت آماده Supabase Auth محسوب نمی‌شود |
| میزبانی رابط پنل | Pages را جدا در نظر بگیرید؛ Supabase هاست عمومی وب/VPS جایگزین نیست |
| دانلود و استخراج روی ویندوز | وظیفه Rust/لانچر، نه دیتابیس یا Edge Function |
| میزبانی پکیج‌های حجیم | Storage رایگان نامناسب؛ محدودیت حجم فایل و انتقال تعیین‌کننده است |
| آمار و لاگ کسب‌وکار | قابل ساخت؛ retention و حریم خصوصی باید طراحی شوند |

Supabase Dashboard پنل کسب‌وکار شما نیست. مدیر پشتیبانی نباید برای مشاهده وضعیت لایسنس، دسترسی مدیریتی مستقیم به پروژه Supabase بگیرد.

## ۴. محدودیت‌های مستند Supabase

بر اساس تعرفه و مستندات رسمی [۱، ۲، ۳]:

| مورد | Free |
|---|---|
| اندازه دیتابیس | ۵۰۰ MB برای هر پروژه |
| منابع پایه | CPU اشتراکی و ۵۰۰ MB RAM |
| فضای Storage | ۱ GB |
| حداکثر فایل در Storage | ۵۰ MB |
| انتقال خروجی | ۵ GB؛ Cached Egress سهمیه جداگانه ۵ GB دارد |
| Auth MAU | ۵۰٬۰۰۰ |
| Edge Function Invocation | ۵۰۰٬۰۰۰ در ماه |
| پروژه فعال | حداکثر ۲ پروژه |
| توقف به علت عدم فعالیت | بعد از یک هفته عدم فعالیت |
| بکاپ خودکار | در Free ارائه نمی‌شود |
| نگهداری لاگ API/Database | یک روز |
| SLA دسترس‌پذیری | در Free ارائه نمی‌شود |

**این اعداد را نباید با ظرفیت تضمین‌شده کاربر اشتباه گرفت.** ۵۰ هزار MAU به معنای توان تضمین‌شده ۵۰ هزار کاربر هم‌زمان نیست. «Unlimited API requests» محدودیت CPU، دیتابیس، انتقال، invocation و کنترل سوءاستفاده را حذف نمی‌کند.

۵ GB خروجی و ۵ GB cached را هم نباید یک مخزن ۱۰ GB قابل مصرف برای هر نوع ترافیک فرض کرد؛ دسته‌بندی مصرف مهم است.

Edge Functions طبق مستندات [۳]:

- حافظه: ۲۵۶ MB.
- زمان فعال‌بودن Worker: Free تا ۱۵۰ ثانیه؛ پلن پولی تا ۴۰۰ ثانیه.
- CPU واقعی: حداکثر ۲ ثانیه برای هر درخواست، جدا از انتظار I/O.

بنابراین API سبک صدور مجوز و ثبت نسخه مناسب است؛ دانلود چندگیگابایتی، استخراج آرشیو و محاسبه هش فایل‌های بازی را از این مسیر عبور ندهید. تولید گروهی لایسنس نیز سقف تعداد، batch و idempotency می‌خواهد.

### Pro چه تغییری می‌دهد؟

تعرفه رسمی از ۲۵ دلار در ماه شروع می‌شود، شامل اعتبار compute به اندازه یک Micro است؛ پس برای یک پروژه Micro معمولی، افزودن دوباره ۱۰ دلار compute به ۲۵ دلار درست نیست. پروژه اضافه، compute بزرگ‌تر، مصرف مازاد و افزونه‌ها هزینه جدا دارند. Pro شامل ۸ GB دیسک دیتابیس، ۱۰۰ GB Storage، ۲۵۰ GB egress و بکاپ روزانه با نگهداری هفت‌روزه است [۱].

برای آزمایش محدود Free منطقی است. برای فروش اشتراک و وابسته‌شدن درآمد به فعال‌سازی، Pro را به‌عنوان بودجه پایه بررسی کنید، نه تضمین دسترس‌پذیری مطلق. پلن Pro نیز جای مانیتورینگ، بکاپ مستقل و تمرین بازیابی را نمی‌گیرد.

## ۵. معماری پیشنهادی

```text
Windows Launcher
  ├─ UI: HTML/CSS/JS
  └─ Native Rust
       ├─ device key + secure local storage
       ├─ license verifier
       ├─ dependency planner
       ├─ streaming downloader + SHA-256
       └─ staged installer + journal + recovery
             │ HTTPS: metadata / entitlement / download authorization
             ▼
      Supabase Edge Functions
             ├─ license activation / refresh
             ├─ package authorization / signed manifest
             ├─ admin actions / audit events
             └─ scoped database operations
                         │
                  Supabase Postgres

Admin SPA on Cloudflare Pages
  ├─ Supabase Auth + MFA
  └─ authorized API / limited RLS-protected reads

Launcher ── direct authorized download ── Private R2 / external host
```

منطق مرجع فعال‌سازی را داخل یک عملیات دیتابیس اتمیک نگه دارید. چند فراخوانی REST پشت سر هم، خودبه‌خود یک تراکنش نمی‌شوند. در صورت استفاده از RPC با `SECURITY DEFINER`، مجوز EXECUTE، `search_path` و ورودی‌ها را محدود و آزمون کنید.

### مدل حداقلی داده

- `games`: شناسه بازی و الگوی اعتبارسنجی نصب.
- `licenses`: HMAC کد، پیشوند نمایشی، tier، وضعیت، زمان‌ها، نسخه ابطال/entitlement.
- `devices`: کلید عمومی دستگاه و متادیتای حداقلی.
- `license_bindings`: اتصال لایسنس به دستگاه با قید یکتای اتصال فعال.
- `activation_attempts`: نتیجه تلاش‌ها بدون کد خام لایسنس.
- `offline_grants`: شناسه صدور و متادیتای مجوز؛ نه محل نگهداری کلید خصوصی.
- `packages` و `package_versions`: پکیج و انتشارهای مستقل و immutable.
- `package_files`: شناسه artifact، SHA-256، اندازه، فرمت و محل دریافت.
- `install_steps`: ترتیب، نوع عملیات محدود و مسیر نسبی مقصد.
- `version_dependencies`: وابستگی به نسخه دقیق یا بازه نسخه.
- `install_reports`: گزارش کلاینت با برچسب «گزارش‌شده»؛ اثبات مستقل نصب نیست.
- `admin_memberships` و `roles`: نقش‌های اختصاصی.
- `audit_events`: رویداد عملیات حساس با شناسه درخواست و retention مشخص.

داده حساس در schema غیرقابل‌دسترسی مستقیم کلاینت نگهداری شود؛ برای جداول exposed از grants حداقلی و RLS استفاده شود. Secret/service-role هرگز در لانچر یا پنل قرار نگیرد [۵]. چون این کلیدها RLS را دور می‌زنند، API دارای دسترسی privileged باید هویت و مجوز هر عملیات را صریحاً بررسی کند.

## ۶. طراحی لایسنس تک‌دستگاهی

### جداسازی دو نوع احراز هویت

- مدیر: حساب Supabase Auth + نقش داخلی + MFA.
- کاربر لانچر: کد لایسنس، بدون اجبار ساخت حساب ایمیل/رمز.

Supabase Auth به‌صورت آماده سیستم «یک کد لایسنس = یک دستگاه» نیست. برای کاربران می‌توان هویت داخلی بدون UI ثبت‌نام ساخت، اما برای شروع یک API اختصاصی لایسنس ساده‌تر و واضح‌تر است. مجوز لایسنس را بدون طراحی صریح اتصال هویت، JWT قابل‌قبول برای Data API فرض نکنید. تنظیم احراز هویت Edge Function باید با این پروتکل اختصاصی هماهنگ باشد؛ غیرفعال‌کردن بررسی JWT پلتفرم فقط وقتی مجاز است که بررسی معتبر خودتان جای آن را بگیرد [۶].

### جریان پیشنهادی

۱. دستگاه یک جفت‌کلید تولید می‌کند؛ کلید خصوصی با امکانات امن ویندوز، ترجیحاً سخت‌افزار پشتیبانی‌شده در صورت امکان، محافظت می‌شود.
۲. کد تصادفی با آنتروپی حداقل ۱۲۸ بیت به API فعال‌سازی فرستاده می‌شود. کدهای قابل حدس یا متکی به تاریخ مناسب نیستند.
۳. سرور HMAC کد با secret سمت سرور را برای lookup محاسبه می‌کند؛ کد خام در لاگ یا دیتابیس روزمره نگهداری نمی‌شود.
۴. اعتبار، انقضا و وضعیت اتصال در تراکنش بررسی و دستگاه متصل می‌شود.
۵. سرور grant امضاشده می‌دهد؛ کلاینت فقط کلید عمومی اعتبارسنجی را دارد.
۶. تمدید و درخواست حساس با اثبات مالکیت کلید دستگاه و challenge/nonce کوتاه‌عمر انجام می‌شود؛ صرف ارسال `device_id` کافی نیست.

ثبت اتصال و entitlement باید اتمیک باشد؛ اگر امضا/پاسخ شبکه پس از ثبت شکست خورد، retry همان دستگاه باید پاسخ معتبر را بازسازی کند، نه اینکه فعال‌سازی دوم حساب شود. Idempotency key و آزمون رقابت درخواست‌ها لازم‌اند.

شناسه سخت‌افزاری تنها نباید معیار باشد: قابل تغییر، قابل جعل و از نظر حریم خصوصی حساس است. تعویض ویندوز یا گم‌شدن کلید دستگاه باید مسیر پشتیبانی روشن داشته باشد.

### حل ابهام‌های سند

- «فقط یک بار فعال‌سازی» را با «فقط یک دستگاه فعال» یکی نگیرید: تمدید و نصب مجدد همان دستگاه نباید خودکار تخلف شوند. بازیابی بدون کلید قبلی می‌تواند نیازمند تأیید مدیر باشد.
- آزادسازی دستگاه توسط مدیر استثنای ثبت‌شده و قابل ممیزی است، نه پاک‌کردن تاریخچه قبلی.
- در نسخه اول `max_devices = 1` ثابت باشد؛ فیلد قابل تغییر تعداد دستگاه در Generator با این قانون ناسازگار است.
- شروع مدت اعتبار هنگام تولید است یا اولین فعال‌سازی؟ پیشنهاد: `created_at` جدا، شروع هنگام اولین فعال‌سازی، با مهلت فعال‌سازی اختیاری.
- بدون حساب، ایمیل یا هویت فروش، «کاربر» در پنل معمولاً دارنده منطقی لایسنس است، نه یک شخص احراز هویت‌شده. آمار کل کاربران باید این تعریف را منعکس کند.

## ۷. سیاست آفلاین ۳+۷ روز

پیشنهاد محتوای مجوز امضاشده:

```text
license_id, device_public_key_thumbprint, tier,
issued_at, refresh_after, offline_until,
subscription_expires_at, entitlement_version,
grant_id, issuer, audience, schema_version, key_id
```

- `refresh_after = issued_at + 3 days`.
- `offline_until = min(issued_at + 10 days, subscription_expires_at)`، مگر مهلت پس از انقضای اشتراک صریحاً تصمیم‌گیری شود.
- روز سوم تلاش برای تمدید؛ هفت روز بعد مهلت قطع اینترنت، نه هفت روز از اولین اجرای آفلاین.
- در اتصال موفق، لغو/تعلیق معتبر سرور باید رعایت شود؛ خطای معتبر «لایسنس لغو شده» با timeout شبکه یکسان نیست.
- لغو آنلاین نمی‌تواند مجوز آفلاین قبلی را روی دستگاه واقعاً آفلاین فوراً باطل کند.
- آزادسازی دستگاه نیز دستگاه قبلی را تا پایان مجوز موجود فوراً بی‌اثر نمی‌کند؛ این پنجره هم‌پوشانی باید در سیاست پشتیبانی پذیرفته شود یا زمان grant کاهش یابد.
- `key_id` و سیاست rotation ضروری‌اند. حذف کلید قدیمی باید با عمر مجوزهای صادرشده هماهنگ شود.

مجوز آفلاین را از session و refresh token مدیران جدا کنید. محتوای امضاشده محرمانه نیست؛ امضا اصالت را می‌دهد نه رمزگذاری.

برای تشخیص عقب‌بردن ساعت از آخرین زمان معتبر سرور، ذخیره محافظت‌شده و زمان monotonic در همان اجرا استفاده شود؛ در برابر snapshot/restore یا دسترسی کامل مدیر سیستم، تضمین مطلق وجود ندارد.

**محدودیت بنیادی:** اگر پکیج‌ها DLL/INI و مود معمولی‌اند، بعد از نصب احتمالاً مستقل از لانچر قابل استفاده و کپی هستند. انقضای لایسنس به‌خودی‌خود مود نصب‌شده را متوقف نمی‌کند. محصول عملاً می‌تواند حق دانلود، آپدیت و خدمات لانچر را بفروشد؛ محدودکردن اجرای خود محتوا نیازمند همکاری آن محتوا/بازی است و نباید وعده ضدکپی قطعی داده شود.

آفلاین برای مشاهده محتوا و مدیریت پکیج‌های موجود قابل تعریف است؛ دریافت فایل جدید اینترنت می‌خواهد. اگر نصب از cache آفلاین مجاز باشد، manifest امضاشده و cache تأییدشده هم لازم است.

## ۸. دانلود، میزبانی و حفاظت محتوا

بزرگ‌ترین تصمیم هزینه‌ای پروژه محل فایل‌های بازی است، نه دیتابیس لایسنس.

مثال محاسباتی، نه پیش‌بینی مصرف واقعی:

```text
100 users × 5 GB full installation = 500 GB outbound traffic
1,000 users × 5 GB = 5,000 GB
```

این مصرف از سهمیه Free بسیار بیشتر است و محدودیت ۵۰ MB هر فایل نیز مستقل از آن وجود دارد [۱، ۲]. فایل حجیم را به قطعات کوچک نشکنید صرفاً برای دورزدن محدودیت؛ پیچیدگی و quota انتقال باقی می‌ماند.

### اگر میزبان شخص ثالث دارید

Backend فقط manifest و مجوز را بدهد و Rust مستقیماً دانلود کند. اما:

- لینک مستقیم عمومی را نمی‌توان با پنهان‌کردن UI خصوصی کرد.
- HTTPS و SHA-256 همراه manifest مورداعتماد لازم‌اند.
- لینک ممکن است کوکی، CAPTCHA، تأیید مرورگر یا تاریخ انقضا داشته باشد؛ «پشتیبانی از میزبان‌های مختلف» به معنی پشتیبانی جادویی از هر سایت نیست.
- HTTP redirectها با کنترل scheme، مقصد و عدم نشت credential دنبال شوند.
- در سرور، URL-checker دلخواه نسازید مگر با دفاع SSRF؛ درخواست به آدرس خصوصی/داخلی و redirect به آن باید مسدود شود.

### اگر کنترل واقعی لینک می‌خواهید

R2 خصوصی + URL امضاشده کوتاه‌عمر گزینه مناسب است. Presigned URL هر دارنده آن را تا زمان انقضا مجاز می‌کند، یک‌بارمصرف یا ذاتاً وابسته به دستگاه نیست؛ URL در گزارش‌ها ثبت نشود [۷]. دوره اعتبار را با دانلودهای طولانی و سیاست Range هماهنگ کنید.

تعرفه رسمی R2 Standard: ۱۰ GB-month، یک میلیون عملیات Class A و ده میلیون Class B رایگان؛ ذخیره اضافه ۰٫۰۱۵ دلار/GB-month و egress اینترنت رایگان است [۸]. «خروجی رایگان» به معنی هزینه صفر کامل نیست: عملیات، Worker احتمالی، ذخیره و نسخه‌های قدیمی حساب می‌شوند. فعال‌کردن سرویس و روش پرداخت مجاز را پیش از اتکا به آن بررسی کنید.

مثال صرفاً هزینه ذخیره R2:

```text
50 GB متوسط در کل ماه → (50 - 10) × $0.015 = $0.60/month
100 GB متوسط در کل ماه → (100 - 10) × $0.015 = $1.35/month
```

فرض: Standard، سهمیه رایگان استفاده‌نشده، عملیات داخل سهمیه، بدون مالیات/هزینه سرویس‌های دیگر. این عدد کل صورتحساب پروژه نیست.

## ۹. موتور نصب: بخش پرریسک‌تر از دیتابیس

### Manifest داده‌محور، نه اجرای کد دلخواه

ادمین باید از مجموعه عملیات شناخته‌شده استفاده کند:

```text
download → verify_hash → extract_to_staging → copy/replace
         → verify_installed_files → commit
```

نسخه schema، حداقل نسخه لانچر و نوع عملیات باید مشخص باشند. اضافه‌کردن پکیج با عملیات موجود به build جدید نیاز ندارد؛ اضافه‌کردن قابلیت جدید موتور نصب ممکن است نیازمند آپدیت لانچر باشد. هدف «هر تغییر بدون آپدیت سورس» را نباید به اجرای JavaScript/PowerShell دلخواه تبدیل کرد.

### کنترل‌های الزامی

- مقاصد فقط نسبی به rootهای مشخص و تأییدشده، با canonicalization.
- رد `..`، مسیر مطلق، drive/UNC path، Windows ADS، نام‌های خاص ویندوز و escape با symlink/junction/reparse point.
- استخراج در staging کنترل‌شده؛ کنترل مسیر هنگام انتقال نهایی نیز تکرار شود. بررسی رشته‌ای پیشوند مسیر کافی نیست.
- محدودیت تعداد فایل، اندازه استخراج‌شده، عمق مسیر و نسبت فشرده‌سازی برای مقابله با archive bomb.
- دانلود streaming و SHA-256 تدریجی؛ اندازه و Content-Length در صورت وجود کنترل شود، ولی فقط به آن اعتماد نشود.
- تشخیص فرمت واقعی، آرشیو ناقص/رمزدار/چندپارته و سیاست روشن پشتیبانی.
- بررسی فضای cache + staging + backup + نصب؛ در درایوهای جدا فضای هر درایو سنجیده شود.
- تشخیص قفل فایل توسط بازی و درخواست بستن بازی، نه بازنویسی کور.
- عدم اجرا به‌عنوان Administrator به‌طور پیش‌فرض؛ مسیر نیازمند ارتقا باید جریان صریح داشته باشد.
- EXE در نسخه اول قابل دریافت/کپی ولی اجرای خودکار خاموش؛ DLL هم بعداً توسط بازی اجرا می‌شود و بی‌خطر فرض نشود.
- ابزار استخراج یا کتابخانه باید روی نمونه‌های واقعی ZIP/RAR/7z آزمون شود. هیچ ابزار unzip منفردی را پشتیبان همه فرمت‌ها فرض نکنید. توزیع ابزار جانبی نیازمند بررسی مجوز و update امنیتی است.

### بازیابی

```text
planned → downloading → verified → staged → applying → verified_install → committed
                                                        └─ failure → recovery/rollback
```

ژورنال پایدار قبل از هر تغییر، فهرست مالکیت فایل‌ها، بکاپ نسخه‌دار و بررسی نتیجه لازم‌اند. اگر برنامه در میانه نصب بسته شد، اجرای بعدی باید recovery را انجام دهد. نصب چندفایلی در پوشه بازی را یک تراکنش اتمیک واقعی فرض نکنید.

در صورت failure وضعیت نصب‌شده ثبت نشود. اگر rollback هم ناقص بود، وضعیت `repair_required` بدهید نه موفقیت کاذب.

فایل‌های حذف‌شده در آپدیت باید فقط در صورت مالکیت و هش مورد انتظار حذف شوند؛ فایل تغییرکرده توسط کاربر یا متعلق به پکیج دیگر بدون سیاست conflict حذف نشود. امکان rollback واقعی هزینه فضای بکاپ و نگهداری artifact نسخه قبلی دارد.

## ۱۰. نسخه‌بندی و وابستگی

- وابستگی به نسخه پکیج تعریف شود، نه فقط شناسه پکیج.
- هنگام انتشار و هنگام نصب cycle detection و topological sort اجرا شود.
- dependencyهای تکراری یک بار نصب شوند؛ تعارض بازه نسخه‌ها نصب را پیش از دانلود متوقف کند.
- هر dependency جداگانه کنترل tier و وضعیت انتشار شود. Normal نباید از طریق بسته واسطه فایل VIP بگیرد.
- ناسازگاری‌ها و مالکیت فایل مشترک نیز به مدل اضافه شوند؛ وجود دو نسخه یک DLL یک conflict واقعی است.
- انتشار `draft → validated → published → deprecated/withdrawn` باشد؛ release منتشرشده immutable بماند.
- لینک موقت دانلود از هویت artifact جدا باشد؛ تغییر میزبان نباید محتوای نسخه منتشرشده را بی‌صدا تغییر دهد.
- SemVer با parser مقایسه شود، نه مقایسه رشته‌ای.
- rollback نسخه، استثنای صریح کنترل‌شده نسبت به سیاست جلوگیری از downgrade باشد.

## ۱۱. پنل مدیریت و امنیت عملیاتی

نقش‌های Owner، License Manager، Content Manager، Support و Viewer داخل برنامه تعریف شوند، مستقل از نقش‌های اعضای پروژه Supabase.

- ثبت‌نام عمومی ادمین خاموش؛ ساخت مدیر با دعوت کنترل‌شده.
- MFA برای مدیران و `aal2` برای عملیات حساس در Backend بررسی شود، نه صرفاً نمایش یک فرم دوم در UI [۴].
- نقش ادمین از فیلد قابل‌ویرایش کاربر گرفته نشود؛ برای عملیات حساس، وضعیت جاری نقش نیز بررسی شود.
- تولید/خروجی لایسنس plaintext فقط در جریان امن اولیه؛ برای خروجی مجدد باید سیاست نگهداری رمزگذاری‌شده آگاهانه داشته باشید. نگهداری صرفاً HMAC اجازه بازیابی متن را نمی‌دهد.
- Audit ثبت‌کننده actor، action، target، زمان، نتیجه و request ID باشد؛ کد لایسنس، token و URL امضاشده حذف/ماسک شوند.
- audit در همان تراکنش عملیات حساس نوشته شود. محدودکردن تغییر آن توسط نقش‌های عادی مفید است؛ مالک کامل دیتابیس همچنان قادر به تغییر داده است، پس ادعای tamper-proof نکنید.
- برای لاگ‌ها retention و تجمیع تعیین شود؛ ثبت هر ثانیه پیشرفت دانلود در دیتابیس اشتباه است.
- Rate limiting بر اساس IP و شناسه‌های HMACشده + محدودیت طول payload، شمار batch و idempotency. محدودیت‌های Auth به‌تنهایی API سفارشی فعال‌سازی را پوشش نمی‌دهند.
- استفاده از Pages یا Cloudflare برای پنل به‌خودی‌خود از API مستقیم Supabase محافظت نمی‌کند؛ مسیر مستقیم هم باید امن باشد.
- تست RLS و API برای anon، device، viewer، support، content و owner، همراه حالت منع دسترسی.
- بکاپ مستقل رمزگذاری‌شده و تمرین restore ضروری است؛ بکاپ دیتابیس جای بکاپ خود فایل‌های Storage/artifact و تنظیمات/secrets را نمی‌گیرد.
- برای اطلاعات دستگاه، IP و سوابق، اطلاع‌رسانی حریم خصوصی، حداقل‌سازی و مدت نگهداری روشن در نظر بگیرید؛ در صورت شمول قوانین اروپا، الزامات GDPR جدا بررسی شود.

## ۱۲. مقایسه با Workers + D1

هر دو مسیر از نظر فنی قابل‌اجرا هستند؛ انتخاب صرفاً براساس بزرگ‌تر بودن عدد فضای رایگان اشتباه است.

| معیار | Supabase | Workers + D1 |
|---|---|---|
| دیتابیس | PostgreSQL؛ مناسب روابط، قیود و تراکنش فعال‌سازی | SQLite مدیریت‌شده؛ نیازمند طراحی اتمیک متناسب با D1 |
| ورود مدیر و MFA | Auth آماده‌تر | نیازمند سرویس احراز هویت/یکپارچه‌سازی جدا یا پیاده‌سازی امن |
| شروع توسعه پنل | ابزارهای Backend بیشتری در یک مجموعه | اجزای بیشتری باید متصل شوند |
| مدل API | REST/RPC + Edge Functions | Workers با کنترل صریح API |
| اتصال فایل خصوصی | میزبان مستقل/R2 | یکپارچگی طبیعی‌تر با R2 |
| کف هزینه پولی | Pro از ۲۵ دلار؛ متناسب با مصرف و منابع | Workers Paid از ۵ دلار؛ مصرف جدا محاسبه می‌شود |

Workers Free طبق مستندات ۱۰۰ هزار درخواست در روز و ۱۰ms CPU در هر invocation دارد. D1 Free پنج میلیون ردیف خوانده‌شده و صد هزار ردیف نوشته‌شده در روز و مجموع ۵ GB ذخیره دارد، اما **هر دیتابیس Free فقط تا ۵۰۰ MB** است؛ نه یک دیتابیس ۵ GB. اسکن ردیف‌ها و indexها روی هزینه مؤثرند [۹، ۱۰].

برای این پروژه، پیشنهاد من Supabase به‌دلیل تکمیل‌بودن ابزارهای مدیریت داده و هویت ادمین‌هاست. اگر حداقل هزینه ثابت مهم‌تر از سرعت توسعه و نگهداری است و تیم تجربه Workers دارد، D1 هم انتخاب معتبر است. دو دیتابیس مرکزی موازی برای لایسنس و پکیج توصیه نمی‌شود.

## ۱۳. هزینه و ظرفیت: فرضیات را از واقعیت جدا کنیم

### سناریو آزمایشی

Free + Pages + میزبان فعلی می‌تواند بدون هزینه جدید کار کند، اگر در سهمیه‌ها باشد؛ تضمین تداوم سرویس تجاری نیست.

مثال بار سبک:

```text
1,000 devices × 10 renewals/month = 10,000 renewals/month
```

این فقط یک محاسبه نمونه است، نه benchmark. کاتالوگ، فعال‌سازی، retry، آمار، پنل و حمله مصرف اضافه دارند؛ تعداد درخواست به‌تنهایی میزان CPU و egress را تعیین نمی‌کند.

### سناریو انتشار تجاری کوچک

Supabase Pro پایه + Pages + فایل‌ها روی میزبان مناسب. اگر فقط یک Micro و منابع داخل سهمیه باشند، پایه Supabase حدود ۲۵ دلار/ماه است؛ کل پروژه ممکن است بیشتر شود [۱].

هزینه‌های فراموش‌شده: دامنه، امضای Windows، CI ویندوز، نگهداری نسخه‌های قدیمی، پشتیبان مستقل، ایمیل بازیابی مدیران و رسیدگی عملیاتی. Self-host کردن Supabase هزینه سرور و نگهداری را حذف نمی‌کند.

اطلاعات لازم برای برآورد نهایی:

۱. تعداد کاربران فعال روزانه/ماهانه و هم‌زمان در زمان انتشار.
۲. مجموع حجم پکیج‌ها و بزرگ‌ترین فایل.
۳. متوسط دانلود ماهانه هر کاربر و نرخ نصب مجدد.
۴. تعداد نسخه‌های قابل rollback و حجم نسخه‌های قدیمی.
۵. محل و قابلیت کنترل میزبان‌های فعلی.
۶. کشور کاربران و دسترسی واقعی به دامنه‌های API/دانلود روی ISPهای هدف.
۷. بودجه مجاز و امکان پرداخت قانونی سرویس‌ها.

دسترسی واقعی برای کاربران هدف، به‌خصوص در شبکه‌های دارای محدودیت، باید از همان شبکه‌ها آزمایش شود؛ از محیط این بررسی نمی‌توان پایداری همه ISPها را نتیجه گرفت.

## ۱۴. انتخاب Tauri و انتشار ویندوز

با توجه به کم‌بودن منطق دامنه فعلی و هدف صریح Rust، اکنون زمان معقول‌تری برای مهاجرت است تا بعد از ساخت موتور کامل نصب. HTML/CSS و بخشی از JS قابل استفاده مجددند؛ `window.uhm` و IPC نیازمند adapter جدید هستند. این تغییر تبدیل خودکار Electron به Tauri نیست.

Tauri قابلیت محدودسازی API با capabilities دارد، اما بررسی مسیر و کنترل امنیتی در Rust همچنان لازم است [۱۲]. بدون تجربه Rust، ادامه Electron هم از نظر فنی ممکن است؛ انتخاب Tauri تضمین ضدکرک‌بودن نیست.

آپدیت خود لانچر با آپدیت پکیج‌ها جدا باشد. Tauri Updater امضای artifact را الزامی می‌کند [۱۳]. این امضا با امضای مجوز آفلاین و Windows Authenticode سه کاربرد جدا هستند و بهتر است کلیدهای مجزا داشته باشند.

نسخه بدون امضای ویندوز ممکن است هشدار یا مسدودشدن داشته باشد؛ هزینه/روش Code Signing را پیش از انتشار عمومی بررسی کنید. حتی گواهی نیز تضمین حذف هر هشدار SmartScreen نیست [۱۴]. کاربران را به خاموش‌کردن آنتی‌ویروس یا Smart App Control هدایت نکنید.

Pages برای UI پنل مناسب است؛ سقف هر asset آن ۲۵ MiB و Free تا ۵۰۰ build ماهانه دارد، پس محل مناسبی برای توزیع پکیج‌های حجیم نیست [۱۱].

## ۱۵. نقشه اجرای پیشنهادی و معیار پذیرش

### مرحله صفر: تثبیت تصمیم‌ها

انتخاب چارچوب، تعریف حق خریداری‌شده (دانلود/آپدیت یا اجرای محتوا)، شروع اعتبار، دستگاه/بازیابی، نصب آفلاین از cache، سیاست EXE، حجم واقعی و میزبان.

خروجی: schema نسخه اول، API contract، threat model و نمونه manifest.

### مرحله یک: نمونه عمودی امن

یک لایسنس، یک دستگاه، یک پکیج ZIP، یک مسیر مقصد و یک گزارش نصب واقعی؛ نه ده‌ها صفحه نمایشی بدون موتور.

معیار پذیرش: درخواست‌های هم‌زمان دو دستگاه دقیقاً یک برنده داشته باشند؛ retry همان دستگاه فعال‌سازی اضافه نسازد؛ Normal به Pro دسترسی نگیرد؛ هش غلط پیش از تغییر فایل بازی رد شود.

### مرحله دو: هسته نصب قابل بازیابی

ZIP/RAR/7z، چند فایل، progress، preflight، staging، backup، journal و recovery.

معیار پذیرش: آرشیو traversal/ADS/junction رد شود؛ قطع برق/kill در مراحل مختلف نصب وضعیت موفق کاذب نسازد؛ کمبود فضا و فایل قفل‌شده توضیح و recovery داشته باشند.

### مرحله سه: مدیریت محتوا و لایسنس

پنل با MFA/RBAC، batch generator، دستگاه، draft/publish و audit.

معیار پذیرش: پکیج جدید با عملیات موجود بدون build لانچر منتشر شود؛ Viewer/Support نتوانند نسخه یا لایسنس را تغییر دهند.

### مرحله چهار: وابستگی، نسخه و آفلاین

حل dependency و conflict، grant امضاشده ۳+۷، rollback کنترل‌شده و updater لانچر.

معیار پذیرش: cycle، duplicate، تعارض نسخه و tier نامجاز پیش از نصب تشخیص داده شوند؛ انقضای grant، تغییر ساعت و مجوز دستگاه دیگر آزموده شوند.

### مرحله پنج: آماده‌سازی انتشار

آزمون Windows واقعی روی مسیر فارسی/دارای فاصله، درایوهای متفاوت، دسترسی محدود و آنتی‌ویروس؛ آزمون بار API، مانیتورینگ quota، تمرین restore و بتای محدود.

این فهرست ترتیب پیشنهادی است، نه برآورد زمان قطعی. زمان/بودجه بدون سنجش تیم و تست استخراج واقعی قابل اتکا نیست.

## ۱۶. جمع‌بندی

پروژه قابل‌ساخت و از نظر معماری مناسب یک محصول واقعی است، اما «لانچر ساده» نیست: سه محصول متصلِ نصب‌کننده، Backend لایسنس و پنل مدیریت است. بیشترین ریسک‌ها نصب امن و قابل بازیابی، مدیریت کلید و دستگاه، حفاظت واقعی لینک‌ها و حق توزیع محتوای مودهاست. برای فایل‌های متعلق به دیگران، مجوز بازتوزیع و تجاری‌سازی باید پیش از انتشار بررسی شود.

**انتخاب پیشنهادی: Supabase برای داده و API و هویت مدیران؛ Pages برای پنل؛ میزبان مستقل یا R2 خصوصی برای فایل‌ها؛ Tauri/Rust برای عملیات محلی.** شروع آزمایشی با Free قابل دفاع است؛ تضمین رایگان‌ماندن انتشار تجاری یا ضدکرک‌شدن محتوا قابل دفاع نیست.
