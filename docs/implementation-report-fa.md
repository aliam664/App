# گزارش پیاده‌سازی عملیاتی — ۲۰۲۶-۱۱-۰۲

## وضعیت تحویل

این تغییر صرفاً طراحی رابط نیست: فایل‌سیستم Native، موتور انتقال و نصب، قراردادها، API و migration تغییر کرده‌اند. ظاهر رسمی UHM، فناوری موجود و منطق لایسنس حفظ شده‌اند. با این حال **کل مشخصات جامع درخواست‌شده هنوز نسخه نهایی و مستقر محسوب نمی‌شود**. موارد باقی‌مانده و وضعیت استقرار در انتهای این گزارش آمده‌اند.

Baseline این مرحله: `d68408aab4d19539e26bf69a0f95faba1d87e6f1` روی `arena/37af8e92-app`.

## آنچه واقعاً پیاده شده است

### کتابخانه و مسیرها

- خواندن SteamPath/InstallPath از رجیستری ویندوز، مسیرهای متداول Steam، `libraryfolders.vdf` و `appmanifest_244210.acf`؛ اعتبارسنجی هر نصب با `acs.exe` و `content`.
- نمایش نصب‌های متعدد، انتخاب نصب فعال، نگهداری مسیرهای انتخاب‌شده و انتخاب دستی معتبر. بازیابی نصب نیمه‌تمام هنگام انتخاب مسیر در worker انجام می‌شود.
- کشف Documents/Assetto Corsa، از جمله مسیر Personal رجیستری، و Content Manager در مسیرهای متداول بازی/Desktop و داده‌های AcTools در LocalAppData. این جست‌وجو سراسری همه درایوها نیست.
- اسکن واقعی Cars، Tracks، Skins و UI لی‌اوت‌ها؛ شامل نصب دستی/Steam/Content Manager که داخل مسیر واقعی بازی قرار گرفته است، نه فقط `installed.json`.
- خواندن JSON واقعی، تصویر PNG/JPEG واقعی با سقف ۴ MB و بررسی magic bytes؛ مقدار غیرقابل‌استخراج «نامشخص» است. HTML متادیتا اجرا نمی‌شود.
- جست‌وجوی نام/پوشه/برند/کشور/سازنده/برچسب؛ فیلتر نوع و مالکیت ثبت‌شده مسیر؛ ترتیب نام/برند/حجم.
- محاسبه حجم فایل‌های موجود و جمع Cars+Tracks بدون دوباره‌شماری Skins/Layout؛ کش ۶۰ ثانیه‌ای به تفکیک root، اسکن اجباری و autoscan هنگام نمایش کتابخانه. پس از نصب کش باطل می‌شود.
- هشدار خطای خواندن، مسیر ناامن و متادیتای مفقود. بررسی فایل‌های مفقود پکیج‌های ثبت‌شده جداست؛ وجود همه مسیرها **به معنی تأیید checksum همه محتوای خارجی نیست**.
- «منبع لانچر» در این نسخه بر اساس مالکیت مسیر در رجیستری است؛ تاریخچه قطعی فایلِ بعداً ویرایش‌شده توسط ابزار خارجی قابل اثبات نیست.

### حذف و بازیابی

- پیش‌نمایش محتوای Car/Track/Skin با فایل‌های واقعی، اندازه و SHA-256؛ کاربر فایل‌ها را جدا انتخاب می‌کند.
- تأیید جداگانه برای فایل‌های خارج از رجیستری لانچر؛ اعتبار پیش‌نمایش ۱۵ دقیقه؛ تغییر محتوا پس از پیش‌نمایش عملیات را متوقف می‌کند.
- جابه‌جایی در همان درایو به `.uhm/quarantine/<uuid>`، manifest قبل از جابه‌جایی و حالت‌های قابل بازیابی برای عملیات نیمه‌تمام.
- بازیابی با preflight تداخل و checksum؛ مقصد موجود جایگزین نمی‌شود. hard-link یا `create_new` از overwrite ناشی از race هنگام restore جلوگیری می‌کند.
- تنها والدهای خالی فایل‌های انتخاب‌شده پاک می‌شوند، نه پوشه‌های خالی نامرتبط. بازیابی والدهای لازم را بازمی‌سازد.
- این عملیات فضا آزاد نمی‌کند؛ حذف دائمی قرنطینه و uninstall وابستگی‌محورِ کل پکیج هنوز ارائه نشده‌اند.

### دانلود و نصب

- فایل `.part` ماندگار با کلید SHA-256؛ استفاده مجدد از فایل کامل فقط پس از hash؛ تلاش مجدد به مجوز نصب تازه نیاز دارد.
- HTTP Range با کنترل دقیق Content-Range/اندازه. پاسخ ۲۰۰ میزبانِ بدون resume از ابتدا نوشته می‌شود؛ ادامه جعلی نمایش داده نمی‌شود. hash نهایی همیشه الزامی است.
- تا پنج mirror برای هر فایل، سه تلاش در هر منبع، کنترل HTTPS/redirect/DNS عمومی و pinning آدرس حل‌شده. HTML صفحه دانلود، captcha و لینک غیرمستقیم به فایل معتبر تبدیل نمی‌شوند.
- از یک تا چهار worker دریافت فایل در هر پکیج، حذف دانلود تکراری یک digest، انتقال flags توقف/لغو به workerها، جمع واقعی شمارنده فایل‌ها، سرعت و ETA تخمینی کل دریافت.
- شبکه async با `read_timeout` سی ثانیه‌ای و بررسی لغو در فاصله‌های یک‌ثانیه‌ای؛ فراخوانی‌های OS مانند DNS یا کپی فایل ممکن است لغو را دیرتر اعمال کنند. رابط اصلی روی worker منتظر I/O نمی‌ماند.
- توقف/ادامه در مرحله دریافت، لغو امن در مراحل مختلف، retry از UI با plan جدید. ترتیب مجوز/وابستگی پکیج‌ها حفظ شده است؛ reorder صف پکیج‌ها پیاده نشده است.
- مسیر دانلود قابل انتخاب و تعداد worker ماندگار؛ نمایش حجم کش و پاک‌سازی تأییدشده فقط فایل‌های شناخته‌شده cache. بکاپ و قرنطینه با این دکمه حذف نمی‌شوند.
- ZIP/RAR/7z، رمز آرشیو و چندبخشی موجود حفظ شده‌اند. ZIP و child extractor هنگام لغو checkpoint دارند. shell یا EXE محتوای ناشناس اجرا نمی‌شود.
- زیرپوشه انتخابی آرشیو، ترتیب مراحل و وابستگی به مراحل قبلی به موتور متصل‌اند.
- پس از استخراج کامل و قبل از تغییر بازی، فهرست واقعی مقصدها/overwriteها/حجم/فضای آزاد/EXEها نمایش داده می‌شود. بسته‌شدن پنجره یا انقضای ۱۵ دقیقه‌ای به معنی انصراف است. approval به UUID پیش‌نمایش جاری متصل است.
- وضعیت مقصدها هنگام پیش‌نمایش و مجدداً قبل از replacement بررسی می‌شود؛ بکاپ باید با فایل تأییدشده تطبیق داشته باشد. journal intent درست پیش از replacement ثبت می‌شود.
- قفل نصب/اسکن/حذف مشترک، قفل cache جدا، حفظ مالکیت سایر پکیج‌ها، بکاپ، rollback، جایگزینی اتمیک و بررسی پس از نوشتن حفظ شده‌اند.
- دانلود و extraction staging پس از commit و rollback موفق پاک می‌شوند؛ بکاپ‌ها و journal عمداً باقی می‌مانند. مدیریت retention بکاپ و پاک‌سازی بعضی stagingهای قدیمیِ حاصل از crash هنوز کامل نیست. بازیابی فعلاً با انتخاب مسیر، عملیات نصب بعدی یا دکمه تنظیمات آغاز می‌شود؛ بازیابی اجباری در boot اضافه نشده است.

### Backend، Builder و صفحات

- شش مقصد قابل استفاده: خانه، دانلود محتوا، دانلود و نصب، کتابخانه من، تنظیمات کتابخانه، تنظیمات برنامه. وب و Windows همان `index.html` و همان سورس را استفاده می‌کنند.
- metadata اختیاری سازگار با manifest قدیمی: توضیح کوتاه، نوع محتوا، سازنده، برند، tags، تصاویر اضافی، زمان انتشار و کانال stable/test.
- Builder همان فیلدها، mirror، زیرپوشه آرشیو و prerequisite مرحله را ذخیره می‌کند؛ ترتیب فایل/مرحله و رمزهای فعلی حفظ شده‌اند.
- migration چهارم سه جدول `package_files`، `package_steps` و `package_dependencies` را با FK/RLS/محرومیت anon/authenticated اضافه می‌کند. JSON فعلی برای سازگاری حفظ شده و children در همان تراکنش sync می‌شوند؛ snapshotهای تاریخی همچنان JSON تغییرناپذیرند.
- کاتالوگ از آخرین snapshot عمومیِ موعدرسیده استفاده می‌کند؛ انتشار آینده یا کانال test، نسخه عمومی قبلی را پنهان نمی‌کند. زمان‌بندی با شرط زمان در query است، نه یک cron جدید.
- `POST /admin/packages/:id/validate`: permission `content.publish`، بررسی ساختار/وابستگی و ثبت audit؛ آزمون نصب یا دسترسی به آپلودر نیست.
- `POST /admin/packages/:id/test-plan`: permission `content.publish` + proof تازه `plan` + grant همان دستگاه/لایسنس فعال؛ plan امضاشده ۱۵ دقیقه‌ای برای draft، با tier معتبر. draft عمومی نمی‌شود. نصب تست به همان موتور Native و همان تأیید واقعی متصل است، نه یک پیام موفقیت نمایشی.
- ساخت draft جدید از snapshot قدیمی و تأیید انتشار/بایگانی؛ شماره پیشنهادی نسخه از head جاری انتخاب می‌شود.
- برای جلوگیری از حذف بی‌صدای فیلدهای جدید توسط API قدیمی، health قابلیت `content-packages-v2` را اعلام می‌کند و ذخیره advanced/validate/test در UI آن را بررسی می‌کنند.

## استقرار و کارهای باقی‌مانده

1. **API و migration جدید روی Supabase deploy نشده‌اند.** فقط پروژه صحیح به‌صورت read-only بررسی شد: `list_migrations` هنوز سه migration تا `202611020003` و `list_edge_functions` تابع فعال `api` نسخه ۸ را نشان دادند. لایسنس مالک، pepper، کلید امضا، جدول لایسنس‌ها و سرویس دیگر کاربر تغییر نکردند. source push یا ساخت وب جای deploy API نیست. استقرار باید migration چهارم، body دقیق `deployment/edge/api.js` و smoke با لایسنس آزمایشی مستقل را شامل شود؛ guard فعلی جلوی ذخیره advanced روی API قدیمی را می‌گیرد.
2. نصب‌کننده قبلی pilot به‌صورت خودکار به‌روزرسانی نشده و release عمومی جدید ساخته نشده است. artifact نصب‌کننده از Windows CI در دسترس است؛ unsigned بودن و نبود auto-updater مانند قبل است.
3. آزمون GUI روی ویندوز واقعیِ کاربر، نصب واقعی بازی/Content Manager، قطع شبکه وسط فایل چندگیگابایتی روی میزبان‌های موردنظر، AV/permission/کمبود فضای واقعی و پایش cold-start/free-tier هنوز انجام نشده‌اند. آزمون Range parser به معنی تضمین resume همه آپلودرها نیست.
4. لی‌اوت فعلاً رکورد UI و تصویر واقعی داخل پیست است؛ تشخیص همه مدل‌های مشترک، حجم مستقل و حذف مستقل layout نیازمند parser مدل/INI و تحلیل reference است. داده‌ای برای این قسمت حدس زده نشده و دکمه حذف غیرعملی ارائه نشده است.
5. CM در مسیر دلخواه، انتخاب/نگهداری دستی مستقل CM و Documents، مقصدهای چند-root مانند Documents برای هر مرحله، import/archive-analysis wizard، تغییرنام فایل انتخابی داخل archive و operationهای بیشتر از copy/extract هنوز کامل نیستند.
6. مدیریت taxonomy دسته‌ها به‌صورت CRUD دیتابیس، پیش‌شرط‌های اجرایی/نسخه‌ای بیشتر، review ویرایش draft در چند تب، reorder صف پکیج، automatic update notification، pagination/virtualization کتابخانه بزرگ، تطبیق معنایی محتوای دستی با شناسه کاتالوگ، retention بکاپ، uninstall وابستگی‌محور و حذف دائمی قرنطینه هنوز تکمیل نشده‌اند.
7. سقف فعلی manifest/expanded data در Native برابر ۱۰۰ GB و سقف operations برابر ۲۰٬۰۰۰ فایل است؛ budget staging/backup محافظه‌کارانه است. filesystem scan سقف عمق ۴۰ و ۵۰۰٬۰۰۰ node در هر traversal دارد. بخشی از وقفه‌های DNS/OS I/O و بعضی کپی‌های بزرگ تا بازگشت syscall قابل قطع آنی نیستند. سیاست فعلی DNS درباره IPv6 همچنان fail-closed است و ممکن است بعضی میزبان‌های dual-stack را رد کند.
8. نمایش همه تصاویر اضافی/متادیتای پکیج در جزئیات کاتالوگ هنوز کامل نیست. metadata خراب یا scan ناقص با «هشدار/نامشخص» نمایش داده می‌شود، نه ادعای فساد قطعی یا حجم دقیق. checksum مرجع برای تمام محتوای خارجی وجود ندارد. آمار cache reuse هنوز به‌صورت یک محور مستقل شبکه در dashboard تفکیک نشده است.

## هزینه و سرویس رایگان

در این مرحله سرویس پولی، storage خارجی یا پروژه جدید ایجاد نشده است. Supabase همان پلن Free با ظرفیت محدود است؛ پکیج‌ها و فایل‌های باینری روی آپلودرهای کاربر می‌مانند. سه جدول جدید metadata را علاوه بر manifest نگه می‌دارند، بنابراین بودجه دیتابیس نامحدود نیست. فایل‌های حجیم از Edge عبور نمی‌کنند. GitHub Actions هم، به‌خصوص برای repository خصوصی، سهمیه دقیقه دارد؛ نتایج ساخت جای تضمین زیرساخت همیشه‌روشن یا بکاپ خارجی خودکار نیستند.
